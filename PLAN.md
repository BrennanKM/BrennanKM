## 1. Blockers found before planning

1. **This is the wrong repository.** `BrennanKM/BrennanKM` is your GitHub profile repo. Its `README.md` is what shows on github.com/BrennanKM. A Next.js monorepo here would either replace your profile page or sit next to it, and Phase 4 of the spec writes a new `README.md` that would overwrite it. This plan is only on branch `claude/new-session-jzkwqx`, which doesn't touch the profile. The app itself needs its own repo (see Q1).
2. **This sandbox can't reach Mapbox or Resend** (the proxy returns 403 for `api.mapbox.com` and `api.resend.com`). So I can't verify these here by running the app:
   - map tiles in screenshots
   - real geocoding
   - real email delivery

   Plan: put both behind small adapters (`lib/geo/geocoder.ts`, `lib/email/mailer.ts`):
   - **Geocoder:** the real Mapbox geocoder in prod; a deterministic fixture geocoder of San Diego and far-away places in local dev and tests.
   - **Mailer:** Resend in prod; Mailpit (the local Supabase mail catcher) in local dev and tests.

   Map screenshots from this sandbox will show the map container with no tiles. I'll say that in each phase report rather than call it verified.
3. **What does work here:**
   - Docker (I had to start the daemon myself).
   - Supabase CLI 2.121 via npm.
   - The Supabase Postgres image from Docker Hub. The default ECR registry is blocked, so local dev sets `SUPABASE_INTERNAL_IMAGE_REGISTRY=docker.io`.
   - Chromium for Playwright and screenshots.

   So the schema, RLS, pgTAP and Playwright work can all run here for real.

## 4. Spec problems I'll fix this way unless you object

| Spec says | Problem | What I'll do |
|---|---|---|
| Drizzle ORM for queries + RLS on every table | Drizzle connects as the `postgres` role, which **bypasses RLS entirely**. RLS would protect nothing on the main code path, and test 6 ("RLS and UI") would pass by accident. | Every user-context query runs inside `withUser(jwt, tx => …)`. That wraps a transaction that does `set local role authenticated` and `set_config('request.jwt.claims', …)`, so RLS applies to Drizzle exactly as it does to supabase-js. Only cron, seed, admin-metrics and the auth trigger use the bypass client. The cost is one extra round trip per request. Test 6 will also try the edit directly against the DB as user B, not just via the UI. |
| `profiles.home_location geography(Point)`, profiles publicly readable | Anyone could read a rider's exact home coordinates. That's a real safety issue for people who park $20k bikes in their garage. | `home_location` stores the **geocoded city centroid** (from `home_city`), never a street address. The column is also excluded from the public select through a column-level grant. The 50-mile filter works the same. |
| `photos jsonb[]` | A Postgres array of jsonb is awkward in Drizzle and in PostgREST, and it gains nothing over a JSON array. | `photos jsonb not null default '[]'`, holding an array of `{path, w, h, blurhash}` objects. |
| Admin can "feature events", "moderate posts/events/users" | The data model has no columns for this. | Add `events.featured_at`, `hidden_at/hidden_by` on content tables, and `profiles.banned_at`. Hidden rows are invisible to non-admins through RLS. |
| `reports` table exists | No screen creates reports. | Add a "Report" item in the overflow menu on events, posts, comments and profiles. |
| Reminder job must be idempotent | Nothing records that a reminder was sent. | Add an `event_reminder_sends` table with a unique `(event_id, user_id)`. The job inserts first and sends second, so a rerun is a no-op. |
| "Inbucket" for magic-link tests | Current Supabase CLI ships **Mailpit**, not Inbucket. | Tests read magic links from Mailpit's API. |
| Supabase magic link + Resend for reminders | Supabase's built-in SMTP is rate-limited to a handful of emails an hour and isn't meant for production. | The README configures Supabase Auth custom SMTP → Resend, so all mail goes through one provider. |
| `max_riders` | The spec doesn't say what happens when an event is full. | When an event is full, "going" is blocked and "maybe" is still allowed. No waitlist. |
| Onboarding gate | This conflicts with "public event links render without login". | The gate applies only to *signed-in* users who haven't finished onboarding. Logged-out visitors can view public pages. |
| Lighthouse ≥ 85 on `/rides` with Mapbox GL | Mapbox GL JS is several hundred KB of JS, which alone threatens the score. | The list renders server-side. Mapbox loads only when the user taps "Map" (dynamic import), and Lighthouse runs against list view. |
| Next.js 15 | Next 16 has been stable for about a year (backport tag 15.5.x still gets patches). | **Decided: Next 16** (see §7). |

## 5. Questions — I need these answered before Phase (a)

**Q1. Which repo does the app go in?** It can't be this one (see §1.1).
- **(a)** You create an empty repo, for example `BrennanKM/throttle`, and tell me. I'll add it to the session and build there. *(Recommended)*
- **(b)** I create it via the GitHub API. I'd need your OK, since it's public-facing, and the private/public setting.

**Q2. How is "day-7 return rate" defined?** This decides whether the Stage B gate is meaningful. Here are three common definitions, from strictest to loosest:
- **(a)** active on day 7 exactly
- **(b)** active on any day from 7 to 13
- **(c)** active on any day from 1 to 7

At **40%**, (a) or (b) is a very high bar for a consumer app; typical D7 is 10–25%. (c) inflates the number with people who just finished onboarding the next morning. I'd use **(b)**, cohorted by signup week, with a minimum cohort size of 20 before the gate counts. But this is your growth bar, so you pick.

**Q3. "≥50% of created events have ≥3 check-ins" — what's in the denominator, and who counts?** As written, the gate measures **how diligent organizers are about tapping "check in"**, not whether people rode. My proposal:
- **Denominator:** published, non-cancelled events whose start time has passed.
- **Count:** check-ins exclude the organizer.
- **Prompt:** organizers get a "Who showed up?" notification 2 hours after the event ends. That's within "basic notifications".

OK?

**Q4. Is Vercel on the Hobby or Pro plan?** Hobby cron runs **once a day** at an imprecise time, so "24h before start" can't actually be hit; reminders would land anywhere from 0 to 24 hours early.
- **Pro:** hourly job, sent 23–25 hours before start.
- **Hobby:** one 9am PT job that sends "your ride tomorrow" for events starting in the next 15–39 hours.

**Q5. Events vs. ride posts naming.** The spec puts *events* at `/rides` but calls the *ride posts* table `rides`, so the code would mean two different things by "ride". I'd keep the user-facing URLs exactly as specced and rename the **table** to `ride_posts` (Drizzle: `ridePosts`). OK?

**Q6. Event invites and growth attribution.** If someone signs up through an *event* invite email (not the personal `/invite/[code]` link), should that set `invited_by` and count as `invite_accepted`? I'd say **yes**, as long as `invited_by` is not already set (first touch wins).

**Q7. Feed ranking "by recency" — recency of what?** For events I'll use the time they were published, not the start time. Otherwise an event two weeks out would sit at the top for two weeks. Upcoming nearby events already get their own "This weekend near you" rail. OK?

**Q8. Keys.** For the final local verification and deploy, I'll need:
- Mapbox public token (`pk.`)
- Resend API key and a verified sending domain
- Google OAuth client ID and secret
- Supabase project URL, anon key and service-role key

None of them are needed to build phases (a)–(i) here. Add them as environment secrets when you're ready; they should never go in chat.

## 7. Decisions (answered 2026-10-15)

| Q | Decision |
|---|---|
| Repo | Brennan creates an empty repo (e.g. `BrennanKM/throttle`); the app is built there, not in the profile repo. |
| Day-7 return | User counts as returned if they have a `session_start` on any of days 7–13 after signup. Grouped by signup week; a group counts toward the gate only once it has ≥ 20 users. |
| Check-in gate | Denominator: published, non-cancelled events whose start time has passed. Organizer's own check-in doesn't count toward the 3. Organizer gets a "Who showed up?" notification ~2h after the event ends. |
| Vercel plan | Hobby. One daily cron at ~9am PT sends "your ride is tomorrow" for `going` RSVPs on events starting 15–39h later. Moving to hourly (Pro) is a one-line `vercel.json` change plus a window constant. |
| Naming | Ride-posts table is `ride_posts` (Drizzle `ridePosts`). URLs unchanged from spec. |
| Event invites | Signing up via an event invite sets `invited_by` and logs `invite_accepted`, unless `invited_by` is already set (first touch wins). |
| Feed order | Events rank by publish time, same as posts. Cursor = `(published_at, id)`. |
| Next.js | Next 16 (current stable), deviating from the spec's 15. |
| Keys | Mapbox, Resend, Google OAuth, Supabase keys are added later as environment secrets, never pasted in chat. Not needed for phases (a)–(i). |
